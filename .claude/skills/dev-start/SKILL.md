アプリの立ち上げを、1つの会話で進める。ここでの合意が、立ち上げでの人の判断になる。このあとは `/dev-build` が土台を作り、立ち上げのすべてを1つの PR にする。
プロトタイプの決まりは [prototype.md](../dev-proto/prototype.md)、人とAIのどちらが決めるかは decisions スキル、土台の中身は foundation スキルに従う。**本番のコードは書かない。**

人に聞くのは、手順2・6の質問（それぞれ1回にまとめる）、手順4の案選び、手順5の触っての直しだけにする。質問には、AIが推す答えを添え、「おすすめで」と答えれば済む形にする。

## 手順

1. GitHub の設定：`.template-version` がなければ、`bash scripts/setup-github.sh` を実行する（Squash merge だけにする、main を守る、Git のフックを有効にする、テンプレートとつなぐ）。gh CLI にログインしていない、GitHub に push していないなどで失敗したら、人間に伝えて止まる
2. 目的を決める：`docs/overview.md` の「目的」「使う人」「主な機能」「やらないこと」「用語」を下書きする
   - `docs/overview.md` が空なら、先に、何を作りたいかを数行で教えてもらう
   - 下書きと、あいまいな点の質問（推す答えつき）を **1回のメッセージで** 出す。技術の話はまだしない
   - 答えを `docs/overview.md` に書く
3. [dev-proto の「準備」](../dev-proto/SKILL.md#準備) を行う（プロトタイプのフォルダ、ひな形、トークン）
4. 雰囲気の案を作る：`docs/overview.md` の主な機能から代表の画面を1つ選び、雰囲気の違う2〜3案を作る。案ごとにトークンを分ける。人間に1つ選んでもらい、選んだ案のトークンを `tokens.css` にし、ほかの案は消す。選んだ案から `docs/ui.md` を書く（値は書かず、使い分けと理由を書く）
5. 主な機能の画面と、画面のつながりを作る。人間に `index.html` から触ってもらい、直しを聞く。合意するまで繰り返す
   - 状態は、0件・大量・読み込み中・エラー・権限なしのうち、その画面で起こるものをすべて作る
   - `docs/overview.md` にない機能・画面を足さない。足したほうがよさそうなら質問する
   - 決まった機能・用語・やらないことは、その場で `docs/overview.md` に、見た目の決まりは `docs/ui.md` に書く
   - 合意したら、作ったすべての画面を状態ごとに撮り、`docs/agreed-screens/<画面>-<状態>.png` に保存する。画面ごとの文言・アイコン・状態ごとの表示は、ここでしかプロトタイプの外に出ない。機能ごとの `/dev-proto` はこの画像から仕様を書き起こす
6. 技術と Issue の分け方を、**1回のメッセージで** 決める
   - 技術：decisions スキルの「人が決めるもの」のうち、このアプリに要るもの（言語・フレームワーク、データベース、デプロイ先、認証、UI の部品ライブラリ、状態管理など）を、用途ごとに表にする。AIが推す案、比べた案、良い点・悪い点、費用を書く。合意した画面と `docs/overview.md` の主な機能から、要る用途を選ぶ
   - Issue の分け方：主な機能を Issue に分ける案（タイトルは「〇〇できる」の1文）と、作る順番。「開発を始められる」は最初に作る
   - 答えを、`docs/overview.md` の「技術」（選んだものと理由を1行）に書く
7. Issue を作る
   - 「開発を始められる」：本文は「技術を決め、テストを先に書いて開発を進められる土台を作る。foundation スキルに沿う。」
   - 主な機能：本文に、関係する画面の名前、合意した画面のつながり（どの画面のどの操作で、どこへ行くか）、関係する `docs/agreed-screens/` の画像のパス、画像に写らない動き（開閉、確認の出方、操作のあとどうなるか）、先に要る機能（Issue 番号）を書く。プロトタイプは本番の作業で読めないので、機能ごとの `/dev-proto` の手がかりを Issue に残す
8. 土台づくりの仕様ファイルを書く
   - main を最新にして、`<「開発を始められる」の番号>-foundation` ブランチを作る
   - `docs/changes/_template.md` をコピーして `docs/changes/<今日の日付 YYYY-MM-DD>-start-development.md` を作る
   - foundation スキルの「仕様」に沿って、「設計」より前を書く。「技術の確認表」には手順6で決めたものを書き、「決まっていないこと」は残さない（手順6で決まらなかったものは、ここで聞く）
9. 次の会話に要るものが、リポジトリと Issue に入っているか見直す。次の会話ではプロトタイプを読めないため
   - この会話で決まった機能・用語・やらないこと・技術が `docs/overview.md` に、見た目の決まりが `docs/ui.md` に入っているか
   - 作った画面と状態のすべてに、`docs/agreed-screens/` の画像があるか
   - 各 Issue に、関係する画面・画面のつながり・画像のパス・画像に写らない動き・先に要る機能が書かれているか
   - 抜けていたら書き足し、書き足したものを人間に伝える
10. プロトタイプのフォルダでコミットする。このリポジトリでは、手順8のブランチに次をコミットする。PR はまだ出さない（`/dev-build` が、土台と一緒に1つの PR にする）
    - `docs/overview.md`・`docs/ui.md`・`docs/agreed-screens/`・仕様ファイル
    - プロトタイプの `tokens.css` を `docs/tokens.css` にコピーしたもの（本番のトークンファイルを作るときの元になる仮置き。本番の置き場所は土台を作るときに決まるため）
    - 手順1でできた `.template-version` と、そのとき消したテンプレートだけで使うファイル（まだコミットされていなければ）
11. 会話を区切り、新しい会話で打つ1行を伝える：`/dev-build <仕様ファイルのパス>`（パスを入れて、そのまま貼れる形で）。あわせて、次を伝える
    - 立ち上げの PR をマージしたら、主な機能を作り始められる（`/dev-proto <番号>`）
    - プロトタイプのフォルダは消さずに残す（機能ごとの `/dev-proto` で使う）

**本番のコードは書かない。マージはしない。**
