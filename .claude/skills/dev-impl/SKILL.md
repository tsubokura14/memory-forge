description: 手順8 タスクを1つ、テストを先に書いて実装し、タスクPRを出す
argument-hint: <docs/changes/の仕様ファイル> <タスク名>
disable-model-invocation: true
---

次のタスクを1つ実装する：$ARGUMENTS

1. 仕様ファイルと、関係する `docs/specs/` を読む。対象のタスクと、それに関係する受け入れ条件・確かめ方を確認する
   - 画面のタスクなら、`docs/ui.md` と、タスクに書かれたスクリーンショット（仕様ファイルと同じ名前のフォルダ）も見る
   - プロトタイプのフォルダは読まない（`docs/process/prototype.md`）
2. main を最新にする。main の仕様ファイルで、次のどちらかに当たれば、伝えて止まる（読んだ仕様ファイルが古かったら、読み直す）
   - 仕様ファイルがない：仕様PRがまだ取り込まれていない
   - このタスクより前のタスクに、チェックの付いていないものがある：前のタスクPRがまだ取り込まれていない。順番に関係のないタスクだと人間が決めたら進めてよい
   - どちらにも当たらなければ、`<Issue番号>-<タスクの英語の短い名前>` ブランチを作る
3. 確かめ方が「テスト」の受け入れ条件について、**テストを先に書き、実行して失敗することを確かめる**（実行はサブエージェント `test-runner` に、書いたテストのファイルを渡して頼む）。コミットする
   - `docs/process/testing.md` に従う。「テストを書かないもの」に当たるテストは書かない
4. テストが通るように実装する。テストが通ったらコミットする
   - 設計で「コメントに残す」とした理由と前提を、コメントに書く。実装中に普通とは違うやり方を選んだとき、「設計」に書かれていない細かい判断をしたときも同じ
   - 複数の場所に関わる決まりができたら、同じ PR で `docs/design.md` に書く。コメントには同じ理由を書かない
   - 画面は、スクリーンショットと `docs/ui.md` に合わせる。値はトークンだけを使い、今ある部品で作れるなら新しい部品を作らない
5. 次のときは **実装を止めて質問する**。推測で進めない
   - 仕様に書かれていない場合が出てきた
   - 仕様や `docs/design.md` と合わない作り方が必要になった
   - 仕様とスクリーンショットが食い違う、または `docs/ui.md` にない部品や見せ方が必要になった
   - 設計のやり方では作れない
   - このタスクの範囲外まで変える必要がある
   人間が決めたら、**先に仕様ファイルを直し**（同じブランチでよい）、それから再開する
6. このタスクの範囲外のもの（ついでの整理、書式の変更など）は変えない。スクリーンショットに写っていても、仕様にないものは作らない
7. 画面のタスクなら、**タスクに書かれた画面だけ** を本番から撮り直す（`docs/process/screenshots.md`）。ほかの画面は撮り直さない
   - その画面について、仕様ファイルの「画面」にある状態のうち、まだ撮っていないものを、撮る対象に足す
   - 撮った画像を開いて、合意したスクリーンショットと見比べる。レイアウト・色・文言・状態ごとの表示の違いは直す。直せない違いは PR に書く
   - 撮り直した `docs/specs/screens/` の画像はコミットする
8. サブエージェント `test-runner` に「全部」を渡し、テスト・Lint・型チェック・画像を比べるテストがすべて通ることを確かめる。失敗したら直して、もう一度頼む
   - 画面のタスクでないのに、またはタスクに書かれていない画面で、画像を比べるテストが失敗したら、撮り直さずに止まり、どの画面がどう変わったかを伝える
9. 仕様ファイルのタスクにチェックを付けてコミットする
10. サブエージェント `pr-check` に、仕様ファイルのパスとタスク名を渡し、差分を照らし合わせてもらう
   - ずれを直してコミットし、手順8からやり直す。直さないものは、理由を PR の「レビューで見てほしいところ」に書く
   - 「確かめてほしいこと」は、PR の「レビューで見てほしいところ」に書く
11. PR を出す
   - タイトル：何をしたかの日本語1文
   - 本文：`.github/pull_request_template.md` に沿い、`Refs #Issue番号`。チェックは実際の状態で埋める
   - 画面を撮り直したなら、撮り直した画像の一覧を、タスクに書かれた画面と並べて「やったこと」に書く
12. CI の結果を `gh pr checks --watch --fail-fast` で、終わるまで待って確かめる（PR を出した直後は、まだ動いているため）。失敗していたら直してから次へ進む
13. PR の URL と、人間がレビューで特に見るべきところを伝える。確かめ方が「触って確かめる」のものがあれば操作の手順を、「コードを見て確かめる」のものがあれば見る場所（ファイルと行）も伝える。画面を撮り直したなら、変わった画像の一覧も伝える

**マージはしない。**
