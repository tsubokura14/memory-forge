$ARGUMENTS の設計とタスク分けをする。**コードはまだ書かない。** 作業は、仕様ファイルがある `<Issue番号>-spec` ブランチ（`/dev-spec` で作ったもの。`git branch --list "*-spec"` で探す）に切り替えてから行う。

1. $ARGUMENTS と同じ名前のフォルダのスクリーンショット、`docs/ui.md`、関係する `docs/specs/`、既存のコードを読む
   - プロトタイプのフォルダは読まない（`docs/process/prototype.md`）
2. 「決まっていないこと」に未回答（`- [ ]`）が残っていたら、先に進まず人間に伝えて止まる
3. 使うライブラリは、インストールされているバージョンの型定義やドキュメントで使い方を確かめる
4. やり方が複数ありうる点は、**書く前に** 選択肢と良い点・悪い点を示して質問する
5. 同じファイルの「設計」に書く：変えるファイル、データの変更、そのやり方を選んだ理由
   - 理由と前提には、仕上げたあとに残す場所も書く。そのコードだけに関わるならコメント、複数の場所に関わるなら `docs/design.md`（`docs/process/code-notes.md`）
   - データの形は、受け入れ条件と使う場面から決める。スクリーンショットに写っている項目名や並びから決めない
   - 画面は、今ある本番の部品で作る。`docs/ui.md` にない部品や見せ方が要るなら、書く前に人間に伝えて決めてもらう
   - `docs/design.md` と食い違う設計になるなら、書く前に人間に伝えて決めてもらう
6. 「確かめ方」に、受け入れ条件ごとに「テスト」「触って確かめる」「コードを見て確かめる」のどれかを書く
   - どれにするかは `docs/process/testing.md` に従う。「テストを書かないもの」はテストにしない
   - 受け入れ条件1つにテスト1つ、とはしない。同じ決まりを別の層でもう一度テストしない
   - すべての受け入れ条件に確かめ方があること
7. 「タスク」に分ける
   - 1タスク = 1ブランチ = 1PR。人間が1回でレビューできる大きさ
   - 「〜ができたら完了」と1文で言える
   - データの変更と画面は別のタスクにする
   - 画面のタスクには、合わせるスクリーンショットのファイル名を書く
   - どのタスクを取り込んでも、アプリが壊れない順番にする（例：まだない画面へのリンクを、その画面より先のタスクで作らない）
8. 人間のレビューを待つ。承認されたらコミットし、PR を出す。ブランチには、このファイルと、同じ名前のスクリーンショットのフォルダだけを入れる
   - タイトル：`<機能の名前>の仕様・設計・タスク`
   - 本文：`.github/pull_request_template.md` に沿い、`Refs #Issue番号`
9. PR の URL を伝える。**マージはしない**
