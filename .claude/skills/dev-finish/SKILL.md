argument-hint: <docs/changes/の仕様ファイル>

$ARGUMENTS の機能を仕上げる。

1. main を最新にしてから仕様ファイルを読み、未チェックのタスクがないか確かめる。残っていたら伝えて止まる
   - タスクのチェックは、タスクPRがマージされて main に入るため
2. 受け入れ条件ごとに、確かめ方と結果を表にする
   - 「テスト」：対応するテストの場所と、実行して通るか（実行はサブエージェント `test-runner` に頼む）
   - 「触って確かめる」：人間が操作する手順
   - 「コードを見て確かめる」：見る場所（ファイルと行）と、そこに書かれている値
3. 人間に、表の「触って確かめる」「コードを見て確かめる」ものを確かめてもらう。問題があれば、新しいタスクとして仕様ファイルに追加することを提案して止まる
4. main から `<Issue番号>-finish` ブランチを作り、変わった動きを `docs/specs/` に反映する
   - 「今どう動くか」だけを現在形で書く。なぜ変えたかは書かない
   - 機能のまとまりごとのファイルに書く。合うファイルがなければ `docs/specs/_template.md` から作る
   - 画面が変わったなら、画面の表（状態と表示）を書き、`docs/specs/screens/` の画像を参照する。画像はタスクPRで本番から撮り直してあるので、コピーしない
   - 表にある状態の画像が `docs/specs/screens/` にない、または画像を比べるテストが失敗するなら、撮り直して（`docs/process/screenshots.md`）同じブランチでコミットする
5. 同じブランチで、仕様ファイルの「設計」と「画面」を、残す場所に反映する
   - 複数の場所に関わるもの：`docs/design.md` に、今どう作られているかを理由・前提つきで書く（タスクPRで書き足し済みなら、食い違いがないかだけ確かめる）。比べた選択肢などの経緯は書かない
   - そのコードだけに関わるもの：コメントに入っているか確かめ、抜けていればコメントに書き足す
   - 同じ理由をコメントと `docs/design.md` の両方に書かない
   - 「画面」に書いた新しい見た目の決まり：`docs/ui.md` に書く
6. 人間のレビューを待つ。承認されたらコミットし、PR を出す
   - タイトル：`<機能の名前>を今の仕様・設計に反映`
   - 本文：`.github/pull_request_template.md` に沿い、**`Closes #Issue番号`**
   - CI の結果を `gh pr checks --watch --fail-fast` で、終わるまで待って確かめる（PR を出した直後は、まだ動いているため）。失敗していたら直す
7. 作業中に出てきた新しい要望やバグがあれば、Issue にする候補として一覧にする（作るのは人間の承認後）
8. この機能で、AIへの指示がうまくいかなかったこと・同じ注意を繰り返したことがあれば、`CLAUDE.md` に足すルールを提案する
9. この機能で出た確認（push や PR 作成などの承認）について、断ったもの・毎回そのまま承認したもの・確認なしで実行されて困ったものがあったかを人間に聞く。あれば、`docs/process/permissions.md` に沿って、権限の変え方の案を出す

**マージはしない。**
