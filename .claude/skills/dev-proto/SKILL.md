画面のプロトタイプを作る。決まりは `docs/process/prototype.md` に従う。**本番のコードは書かない。**

$ARGUMENTS が空なら「立ち上げ（手順3）」、仕様ファイルなら「変更（手順6）」として進める。

## 準備

1. `docs/process/prototype.md`、`docs/ui.md` を読む
2. プロトタイプのフォルダが作業ディレクトリに入っているか確かめる。入っていなければ、人間に場所を聞き、フォルダを作って `/add-dir <フォルダ>` で加えてもらうよう頼んで止まる
   - このリポジトリの外で、本番の作業の作業ディレクトリに入らない場所にする
   - 加えるのはこの会話だけ。設定には保存しない
3. フォルダが空なら、次を作り、`git init` してコミットする
   - `index.html`：画面と状態の一覧。人間が最初に開くページ
   - `pages/<画面の英語名>.html`：1画面1ファイル。状態は `?state=<状態>` で切り替える。表示用のデータは、ページに決まった値で書く
   - `tokens.css`：トークン。Tailwind の CLI でビルドし、ビルド結果の CSS もコミットする（ファイルをブラウザで開くだけで見られるように）
   - スクリーンショットを撮るスクリプト：Playwright で、画面と状態の組み合わせごとに `<画面>-<状態>.png` を保存する。保存先は引数で受け取る
4. 本番のトークンファイル（場所は `docs/ui.md` の「トークン」）があれば、`tokens.css` に上書きでコピーする。プロトタイプから本番へはコピーしない

## 立ち上げ（$ARGUMENTS が空）

1. 雰囲気の案を作る：`docs/overview.md` の主な機能から代表の画面を1つ選び、雰囲気の違う2〜3案を作る。案ごとにトークンを分ける
2. 人間に1つ選んでもらう。選んだ案のトークンを `tokens.css` にし、ほかの案は消す
3. 選んだ案から `docs/ui.md` を書く。値は書かず、使い分けと理由を書く
4. 主な機能の画面と、画面のつながりを作る
   - 状態は、0件・大量・読み込み中・エラー・権限なしのうち、その画面で起こるものをすべて作る
   - `docs/overview.md` にない機能・画面を足さない。足したほうがよさそうなら質問する
5. 人間に `index.html` から触ってもらい、直しを聞く。合意するまで繰り返す
   - 決まった機能・用語・やらないことは、その場で `docs/overview.md` に書く
   - 決まった見た目の決まりは、その場で `docs/ui.md` に書く
6. 主な機能を Issue に分ける案を出す（タイトルは「〇〇できる」の1文。本文に関係する画面の名前）。人間が承認したら Issue を作る
7. プロトタイプのフォルダでコミットする。このリポジトリでは、main から `ui-foundation` ブランチを作り、`docs/ui.md` と `docs/overview.md` をコミットして PR を出す
   - タイトル：`画面の雰囲気と主な機能を決める`
   - 本文：`.github/pull_request_template.md` に沿う。対応する Issue はないので、`Refs` の行は消す
8. 会話を区切ってから、手順4（技術を決める）に進むよう伝える

## 変更（$ARGUMENTS が仕様ファイル）

1. 仕様ファイルがある `<Issue番号>-spec` ブランチ（`/dev-spec` で作ったもの。`git branch --list "*-spec"` で探す）に切り替える。$ARGUMENTS と、関係する `docs/specs/`（`docs/specs/screens/` のスクリーンショットを含む）を読む。「決まっていないこと」に未回答（`- [ ]`）が残っていたら、人間に伝えて止まる
2. 変わる画面のプロトタイプが `docs/specs/screens/` と違っていたら（本番だけが直されたなど）、先にプロトタイプを今の本番に合わせる。プロトタイプにない画面は、スクリーンショットと `docs/specs/` から作る
3. 仕様ファイルの「受け入れ条件」と「画面」に沿って、変わる画面を作る。「画面」に書いた状態はすべて作る
   - 仕様にない要素を足さない。足したほうがよさそうなら質問する
4. 人間に `index.html` から触ってもらい、直しを聞く。合意するまで繰り返す
   - 決まったことは、その場で仕様ファイルに書き戻す（「受け入れ条件」「画面」「決まっていないこと」）。プロトタイプにしか残っていない決めごとを作らない
   - `docs/ui.md` にない見た目の決まりができたら、仕様ファイルの「画面」に書く（`docs/ui.md` へは仕上げのときに移す）
5. 合意したら、変わった画面の状態ごとにスクリーンショットを撮る
   - 保存先：`docs/changes/<仕様ファイルと同じ名前>/<画面>-<状態>.png`
   - 仕様ファイルの「画面」から、画像を参照する
6. プロトタイプのフォルダでコミットする。このリポジトリでは、仕様ファイルとスクリーンショットを `<Issue番号>-spec` ブランチにコミットする（PR は `/dev-plan` で出す）
7. 会話を区切ってから `/dev-plan $ARGUMENTS` に進むよう伝える（本番の作業に、プロトタイプの中身を持ち込まないため）

**本番のコードは書かない。マージはしない。**
