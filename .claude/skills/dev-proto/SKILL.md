機能の仕様を、プロトタイプで決める。ここでの合意が、人の判断の1回目になる。合意したあとは、AIが止まらずに作る。
プロトタイプの決まりは [prototype.md](prototype.md)、人とAIのどちらが決めるかは decisions スキルに従う。**本番のコードは書かない。**

対象は、コマンドのあとに書かれた Issue 番号（以下 `<番号>`）の機能。引数が空なら、立ち上げは `/dev-start` で行うと伝えて止まる。
「準備」は、`/dev-start` からも使う。

## 準備

1. [prototype.md](prototype.md)、`docs/ui.md` を読む
2. プロトタイプのフォルダが作業ディレクトリに入っているか確かめる。入っていなければ、人間に場所を聞き、フォルダを作って `/add-dir <フォルダ>` で加えてもらうよう頼んで止まる。機能で、Issue から画面が変わらないと分かるなら、加えずに進めてよい（下の「手順」の4で作ると決まったら、そこで頼む）
   - このリポジトリの外で、本番の作業の作業ディレクトリに入らない場所にする
   - 加えるのはこの会話だけ。設定には保存しない
3. フォルダが空なら、次を作り、`git init` してコミットする
   - `index.html`：画面と状態の一覧。人間が最初に開くページ
   - `pages/<画面の英語名>.html`：1画面1ファイル。状態は `?state=<状態>` で切り替える。表示用のデータは、ページに決まった値で書く
   - `tokens.css`：トークン。Tailwind の CLI でビルドし、ビルド結果の CSS もコミットする（ファイルをブラウザで開くだけで見られるように）
   - スクリーンショットを撮るスクリプト：Playwright で、画面と状態の組み合わせごとに `<画面>-<状態>.png` を保存する。保存先は引数で受け取る
4. 本番のトークンファイル（場所は `docs/ui.md` の「トークン」）があれば、`tokens.css` に上書きでコピーする。プロトタイプから本番へはコピーしない

## 手順

人間に聞くのは、**手順5の質問（1回）** と **手順7の触っての直し** だけにする。それ以外はAIが下書きし、決めてよいものは決める。

1. `gh issue view <番号>` で Issue を読む。`docs/overview.md`、`docs/design.md`、関係しそうな `docs/specs/`（`docs/specs/screens/` を含む）を読む
   - Issue に `docs/agreed-screens/` の画像が書かれていたら、その画面は立ち上げのプロトタイプで合意済み。画像を読む
2. main を最新にして `<番号>-<英語の短い名前>` ブランチを作る。`docs/changes/_template.md` をコピーして `docs/changes/<今日の日付 YYYY-MM-DD>-<何をするかの英語名>.md` を作り、コミットする
   - 名前は機能名ではなく「何をするか」（例：`add-due-date`）。同じ名前のファイルがあれば変える
3. 仕様ファイルの「設計」より前を、すべて下書きする
   - 使う場面：具体的な人・データ・操作の順で、1〜3つ書く（例：期限が3日後のタスクを持つ人が、一覧を開くと〜と表示される）
   - 受け入れ条件：エラーのとき、データが空のとき、ログインしていないとき、境界の値も書く。技術の話は書かない（技術は「技術の確認表」と「設計」に書く）
   - 画面：画面が変わるなら、変わる画面と、0件・大量・読み込み中・エラー・権限なしのうちその画面で起こる状態ごとの表示を書く。合意済みの画面は、`docs/agreed-screens/` の画像と Issue の本文から書き起こす
   - 技術の確認表：すべての項目を埋める（decisions スキル）
   - 先に要る機能：この機能が頼る、ほかの機能の Issue。なければ「なし」
   - 決まっていないところは、decisions スキルで分ける。「AIが決めてよいもの」は決めて「AIが決めたこと」に書く。「人が決めるもの」だけを「決まっていないこと」に質問として書き、それぞれに **AIが推す答え** と、比べた案の良い点・悪い点を添える
   - `docs/specs/` や `docs/overview.md` の用語と食い違わないか、`docs/overview.md` の「やらないこと」に触れていないか、1つの機能として大きすぎないか（大きすぎるなら分け方の案を「決まっていないこと」に）も見る
4. プロトタイプが要るかを決める
   - 合意済みの画面があるか、下の表で「作る」に当たるなら、作る
   - 作らないなら、手順6・7を飛ばす

   | プロトタイプを作る | 作らない |
   | --- | --- |
   | 新しい画面 | 文言だけの変更 |
   | 画面の流れやレイアウトが変わる | 今ある見せ方の範囲で、項目を足す・減らす |
   | `docs/ui.md` にない見せ方や部品が要る | 内部処理だけの変更 |
   | 操作の手触りを言葉で決めにくい | バグ修正 |

5. **1回のメッセージで** 人間に確かめる。人間が「おすすめで」と答えれば済む形にする
   - 自分の理解を数行で言い換える（「〜という理解で合っていますか」）。使う場面を1つ添える
   - 「決まっていないこと」の質問を、AIが推す答えと一緒に並べる
   - 「AIが決めたこと」の一覧（直したいものがあれば言ってもらう）
   - プロトタイプを作るかどうか
   - 答えを仕様ファイルに反映してコミットする。「決まっていないこと」には答えも残す（`- [x] 質問 → 答え`）
6. プロトタイプを作る。変わる画面ごとに、どこから始めるかを決める
   - **合意済みの画面**（`docs/agreed-screens/` に画像がある。立ち上げで合意し、まだ本番にない）：プロトタイプを作り直さない。本番に合わせることもしない。プロトタイプと仕様ファイルを見比べ、食い違いがあれば手順7で見せて、どちらに合わせるかを選んでもらう
   - **本番にある画面**：プロトタイプが `docs/specs/screens/` と違っていたら（本番だけが直されたなど）、先にプロトタイプを今の本番に合わせる
   - **プロトタイプにない画面**：スクリーンショットと `docs/specs/` から作る
   - 仕様ファイルの「受け入れ条件」と「画面」に沿って作る。「画面」に書いた状態はすべて作る。仕様にない要素は足さない
7. 人間に `index.html` から触ってもらい、直しを聞く。合意するまで繰り返す
   - 決まったことは、その場で仕様ファイルに書き戻す（「受け入れ条件」「画面」「決まっていないこと」「技術の確認表」）。プロトタイプにしか残っていない決めごとを作らない
   - `docs/ui.md` にない見た目の決まりができたら、仕様ファイルの「画面」に書く（`docs/ui.md` へは機能を仕上げるときに移す）
   - 直しの中で、受け入れ条件が変わったり、「人が決めるもの」に当たる話が出たりしたら、その場で聞いて書く
8. 合意の前に、技術の確認表を見直す。直しで変わった項目がないか、空欄がないか。「人が決めるもの」で、`docs/overview.md`・`docs/design.md` にも仕様ファイルにも答えがないものが残っていれば、ここで聞く
9. 合意したら、変わった画面の状態ごとにスクリーンショットを撮る
   - 保存先：`docs/changes/<仕様ファイルと同じ名前>/<画面>-<状態>.png`
   - 仕様ファイルの「画面」から、画像を参照する
10. 次の会話（または実装のサブエージェント）に要るものが、仕様ファイルに入っているか見直す。プロトタイプは本番の作業で読めないため
    - この会話で決まったこと（直しの中で決めた動き・文言・見た目を含む）が、仕様ファイルに入っているか
    - 「画面」に書いた状態のすべてに、スクリーンショットがあり、参照が切れていないか
    - 「決まっていないこと」に未回答（`- [ ]`）がなく、「技術の確認表」に空欄がないか
    - 抜けていたら書き足し、書き足したものを人間に伝える
11. プロトタイプのフォルダでコミットする。このリポジトリでは、仕様ファイルとスクリーンショットをブランチにコミットする。PR はまだ出さない（`/dev-build` が、実装と一緒に1つの PR にする）
12. 会話を区切り、新しい会話で打つ1行を伝える：`/dev-build <仕様ファイルのパス>`（パスを入れて、そのまま貼れる形で）。ほかにも合意済みの機能があれば、まとめて作る `/dev-run <Issue番号...>` も使えると伝える。これで人の判断の1回目は終わり、次は PR を見てマージするときになる。会話を区切るのは、本番の作業に、プロトタイプの中身を持ち込まないため

**本番のコードは書かない。マージはしない。**
