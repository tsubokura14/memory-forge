コマンドのあとに書かれた Issue の機能を、順に作る。どの機能も、`/dev-proto` で人と合意済みのもの。
人がいなくても進むように、**1つの機能で止まっても、全体は止めない**。止まった機能は、聞きたいことを残して飛ばし、ほかの機能を進める。人は最後にまとめて答え、たまった PR をマージする。

1つずつの作り方は [dev-build](../dev-build/SKILL.md) と同じ。ここには、続けて作るための違いだけを書く。

## 始める前に

1. 作業ツリーに、コミットしていない変更がないか確かめる（`git status`）。あれば、何があるかを伝えて止まる（機能ごとにブランチを切り替えるため）
2. Issue ごとに、作れるかを確かめて表にする
   - 仕様ファイルのあるブランチ（`git branch --list "<Issue番号>-*"`）がない：`/dev-proto` がまだ。飛ばす
   - 「決まっていないこと」に未回答（`- [ ]`）がある、または「技術の確認表」に空欄がある：合意が済んでいない。飛ばす
   - 「先に要る機能」に、まだ main に入っていない Issue がある：飛ばす。PR を積み重ねると、Squash merge で取り込むたびに作り直しになるため（同じ回で作る機能に頼る場合も、その機能がマージされるまで待つ）
3. 作れるものを、「先に要る機能」に沿った順に並べる。表（作るもの・飛ばすものと理由）を伝えて、そのまま始める（ここでは止まらない）

## 機能ごとに

並べた順に、1つずつ [dev-build](../dev-build/SKILL.md) の「準備」から「仕上げと PR」までを行う。違いは次のとおり。

- **dev-build で「止まって人に聞く」とき**（人が決めるものの漏れ、3回直してもテストが通らない、タスクの外の画面で画像の比較が失敗した、など）は、止まらずに、その機能を「止まった」にして次の機能へ進む
  1. 聞きたいことを、仕様ファイルの「決まっていないこと」に `- [ ]` で書く。AIが推す答えと、比べた案の良い点・悪い点も書く。テストが通らないなどの場合は、失敗の一覧と試したことを書く
  2. 作りかけの変更があれば、`作りかけ：<タスク名>` というメッセージでコミットする（ブランチを切り替えると、ほかの機能に混ざるため）
  3. 仕様ファイルをコミットし、ブランチを push する。PR は出さない
- CI が失敗して、`implementer` に3回直させても通らなければ、同じく「止まった」にする（PR は出したまま、本文の「レビューで見てほしいところ」に書く）
- 次の機能に移る前に、作業ツリーに変更が残っていないことを確かめる
- 機能を1つ終えるごとに、仕様ファイルのパスと結果（PR の URL か、止まった理由）を短く書き残す。会話が長くなって前のことを忘れても、最後の表を作れるように

## 最後に伝えること

1. 機能ごとの結果の表
   - PR を出した：PR の URL。人がマージの前に見るところ（dev-build の「仕上げと PR」の最後と同じ）
   - 止まった：何を聞きたいか（推す答えつき）、ブランチ。答えたあとに打つ1行 `/dev-build <仕様ファイルのパス>`（設計とチェック済みのタスクは飛ばして、続きから作る）
   - 飛ばした：理由（`/dev-proto` がまだ、先に要る機能がまだ main にない、など）
2. マージする順番：「先に要る機能」があるものは、頼られる側を先にマージする
3. 飛ばした機能のうち、PR をマージすれば作れるようになるもの：マージのあとに打つ1行 `/dev-run <Issue番号...>`
4. dev-build の [finish.md](../dev-build/finish.md) の「PR を出したあと」を、すべての機能の分をまとめて伝える

**マージはしない。**
