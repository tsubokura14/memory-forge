コマンドのあとに書かれた仕様ファイルの機能を、PR まで作る。何を作るかは `/dev-proto` で人と合意済み。
**人には聞かずに進める。** 止まるのは、decisions スキルの「人が決めるもの」が決まっていないと分かったときと、下に書いたときだけ。人は最後に PR を見てマージする。

この会話は進行役になる。コードは、タスクごとにサブエージェント `implementer` が、新しい文脈で書く（この会話の長さとプロトタイプの記憶を、実装に持ち込まないため）。

引数が Issue 番号なら、仕様はまだない。`/dev-proto <番号>` を使うよう伝えて止まる。

## 準備

1. 仕様ファイルがあるブランチに切り替える（`git branch --list "<Issue番号>-*"` で探す。複数あれば、`git show <ブランチ>:<仕様ファイル>` で、そのファイルがあるブランチを選ぶ）。この1本のブランチで、機能の PR まで作る
2. 仕様ファイルと同じ名前のフォルダのスクリーンショット、`docs/ui.md`、`docs/design.md`、関係する `docs/specs/`、既存のコードを読む
3. 次に当たれば、伝えて止まる（`/dev-proto` での合意が済んでいない）
   - 「決まっていないこと」に未回答（`- [ ]`）がある
   - 「技術の確認表」に空欄がある
4. 「先に要る機能」の Issue が、すべて閉じていて、その変更が main に入っているか確かめる（`gh issue view <番号> --json state`）。入っていなければ、どれが足りないかを伝えて止まる。このブランチを作ったあとに main に入ったものは、`git fetch` のあと `git merge origin/main` で取り込む

## 設計とタスク

設計とタスクがもう書かれていれば（止まったあとの再開）、飛ばす。

1. 使うライブラリは、インストールされているバージョンの型定義やドキュメントで使い方を確かめる（まだ入れていないものは、公式のドキュメントで）
2. やり方が複数ありうる点は、decisions スキルで分ける
   - 「AIが決めてよいもの」：選び、「AIが決めたこと」に、選んだもの・理由・比べた案を書く（経緯の置き場所はここだけ）
   - 「人が決めるもの」で、仕様ファイル・`docs/design.md`・`docs/overview.md` に答えがないもの：止まって、AIが推す案と比べた案を示して聞く。答えを先に仕様ファイル（「決まっていないこと」と「技術の確認表」）に書く
3. 「設計」に書く：変えるファイル、データの変更、そのやり方を選んだ理由
   - 理由と前提には、機能を仕上げたあとに残す場所（コメントか `docs/design.md`）も書く（code-notes スキル）
   - データの形は、受け入れ条件と使う場面から決める。スクリーンショットに写っている項目名や並びから決めない
   - 画面は、今ある本番の部品で作る。`docs/ui.md` にない部品や見せ方が要り、仕様ファイルの「画面」にも書かれていなければ、手順2の「人が決めるもの」として扱う
   - `docs/design.md` と食い違う設計になるなら、手順2の「人が決めるもの」として扱う
4. 「確かめ方」に、受け入れ条件ごとに「テスト」「触って確かめる」「コードを見て確かめる」のどれかを書く（testing スキル）。すべての受け入れ条件に確かめ方があること。操作の流れは、できるだけ「テスト」（画面を動かすテスト）にする
5. 「タスク」に分ける
   - 1タスクは、`implementer` が1回で作り終えられる大きさ。「〜ができたら完了」と1文で言える
   - データの変更と画面は別のタスクにする
   - 画面のタスクには、合わせるスクリーンショットのファイル名を書く
   - 前のタスクだけを取り込んだ状態でもアプリが壊れない順番にする（レビューでコミットを順に追えるように）
6. コミットする

## 実装（タスクごと）

チェックの付いていないタスクを、上から1つずつ進める。

1. `implementer` に、仕様ファイルのパスとタスク名を渡す。仕様ファイルにないこと（プロトタイプで見たものなど）は渡さない
   - ブランチの最後に `作りかけ：<タスク名>` のコミットがあれば（`/dev-run` で止まった機能の再開）、そのタスクの続きから作るよう伝える
2. 「止まった」が返ってきたら
   - decisions スキルの「人が決めるもの」なら：AIが推す答えと比べた案を示して人に聞き、止まる。答えを先に仕様ファイルに書いてから、同じタスクをもう一度 `implementer` に渡す
   - 「AIが決めてよいもの」なら：決めて「AIが決めたこと」に書き、もう一度渡す
3. サブエージェント `test-runner` に「全部」を渡す。失敗したら、失敗の一覧を `implementer` に渡して直させ、もう一度 `test-runner` に頼む
   - 3回直しても通らなければ、止まって、失敗の一覧と試したことを伝える
   - 画像を比べるテストが、タスクに書かれた画面以外で失敗したら、直させずに止まる（screenshots スキル）
4. 仕様ファイルのタスクにチェックを付けてコミットする

`CLAUDE.project.md` にテストのコマンドがまだなく、`test-runner` が「コマンドが未設定」と返したら、失敗として扱わない（土台を作る前の機能だけ）。

## 仕上げと PR

1. [finish.md](finish.md) の「PR を出す前」を行う
2. サブエージェント `pr-check` に、仕様ファイルのパスを渡し、ブランチ全体の差分を照らし合わせてもらう
   - ずれは `implementer` に渡して直させ、`test-runner` で「全部」をもう一度確かめる
   - 直さないものは、理由を PR の「レビューで見てほしいところ」に書く。「確かめてほしいこと」も同じ欄に書く
3. push して PR を出す
   - タイトル：何をしたかの日本語1文
   - 本文：`.github/pull_request_template.md` に沿い、`Closes #Issue番号`。チェックは実際の状態で埋める
4. CI の結果を `gh pr checks --watch --fail-fast` で、終わるまで待って確かめる（PR を出した直後は、まだ動いているため）。失敗していたら `implementer` に直させ、push してもう一度確かめる
   - `no checks reported` と出たら（exit 1 で終わる）、失敗として扱わない。`.github/workflows/` がなければ、CI はまだないので確かめずに進み、最後に「CI がまだないので確かめていない」と伝える。あれば、チェックがまだ登録されていないので、少し待ってからもう一度確かめる
5. PR の URL と、人がマージの前に見るところを伝える：AIが決めたこと、「触って確かめる」ものの操作の手順、「コードを見て確かめる」ものの場所（ファイルと行）、撮り直した画像の一覧。[finish.md](finish.md) の「PR を出したあと」も伝える

**マージはしない。**
