# データベースの接続で、証明書を確かめるやり方を明示する（#38）

## なぜ

テストやアプリを立ち上げるたびに、データベースにつなぐライブラリ（`pg`）が警告を出している。今の接続先の書き方（`sslmode=require`）は、次の大きな版で今より弱い確かめ方に変わる、という警告。

今はサーバーの証明書を確かめてからつないでいる。版を上げたときに、知らないうちに証明書を確かめなくならないよう、今の確かめ方をはっきり書いておく。

気づいたきっかけは、#3 の画面のテストと CI のログ。

## 影響する今の仕様

- `docs/specs/` の動きは変わらない（画面もログインの動きも同じ）
- 変わるのは、データベースへのつなぎ方（`docs/design.md` の「データベースのつながり方」）

## 使う場面

1. 自分が手元で `npm test` や `npm run dev` を実行すると、証明書の確かめ方についての警告が出ない
2. 自分が PR を出すと、CI のログと Preview の公開のログに同じ警告が出ず、テストが通る。Preview で sign in できる
3. 自分が本番の URL で sign in すると、今までどおり Home が出る。本番のログにも同じ警告が出ない

## 受け入れ条件

- 本番・Preview・手元の開発・手元のテスト・CI のどこでも、データベースにつなぐとき、サーバーの証明書を確かめる（今と同じ強さ）
- 本番・Preview・手元の開発・手元のテスト・CI のどこでも、証明書の確かめ方についての警告が出ない
- 証明書を確かめられない接続先には、つながらない
- 本番と Preview で、今までどおり sign in でき、Home が出る
- 手元の開発・手元のテスト・CI は、今までどおり動く

## 画面

画面は変わらない。

## やらないこと

- アプリの画面・ログインの動きは変えない
- データベースの場所（Neon のプロジェクトやブランチ）は変えない（#35 で決めたまま）
- 証明書を自分で用意して確かめる（自分で選んだ証明書を置く）ことはしない

## 決まっていないこと

- [x] 本番と Preview の接続先は、#35 から Neon が管理する Vercel 連携が入れている。Preview は公開のたびに作られるので、人間が URL を書き換えられない。Issue の案（接続先の URL を書き換える）だけでは本番と Preview に届かないかもしれない。アプリの側で確かめ方を指定するやり方も、設計で比べてよい？ → 比べてよい
- [x] 手元（`.env.local`・`.env.test`）と GitHub の Secret の接続先は、人間が書き換える必要がある？ → 設計で決める（アプリの側で指定するやり方を選べば、書き換えなくてよい）
- [x] 警告は、手元の開発・手元のテスト・CI で出なくなればよい？ Vercel のログ（本番と Preview）でも出なくなる必要がある？ → Vercel のログでも出なくする（本番で弱くならないことが目的のため）
- [x] 「証明書を確かめられない接続先には、つながらない」は、触って確かめなくてよい？（わざと悪い接続先を作るのは手間がかかる） → 触って確かめない。設計で決めた確かめ方（コードを見るなど）で足りる
- [x] 自分で用意した証明書を置いて確かめることは、やらないことにしてよい？ → よい

## 調べたこと

インストールされている `pg` 8.23.1・`pg-connection-string` 2.14.1・`drizzle-kit` 0.31.11 のコードで確かめた（2026-10-21）

- 今の版は、URL の `sslmode=require`（`prefer`・`verify-ca` も）を `verify-full`（証明書と接続先の名前を確かめる）と同じに扱い、そのうえで警告を出す。次の大きな版（`pg` v9）では、`require` は証明書を確かめなくなる。警告を出さずに今の確かめ方を保つには、`sslmode=verify-full` と書く
- URL に `sslmode` があると、その値が優先される。`new Pool()` に `ssl` の設定を別に渡しても、URL から読んだ値で上書きされ、警告も出る。環境変数 `PGSSLMODE` も、URL に `sslmode` があると使われない
- drizzle-kit も、中で `pg` の `Pool` に URL をそのまま渡している（`connectionString`）

---

## 設計

アプリの側で、データベースにつなぐ前に、接続先の URL の `sslmode` を `verify-full` に置き換える。接続先の値（`.env.local`・`.env.test`・GitHub の Secret・Vercel）は、どれも変えない。

### 変えるファイル

- 新規：`src/server/db/connection-url.ts`
  - 接続先の URL を受け取り、`sslmode` を `verify-full` にした URL を返す関数を1つ置く
    - `sslmode` があれば（`require`・`disable` なども）`verify-full` に置き換える。なければ足す
    - ほかの値（`channel_binding` など）とユーザー名・パスワードは変えない
    - 空や、ないときは、そのまま返す（今と同じく、つなぐときに失敗する）。この細かい扱いは、関数のコメントに書く
- 新規：`src/server/db/connection-url.test.ts`（「確かめ方」）
- つなぐ4か所で、URL をこの関数に通してから渡す
  - `src/server/db/client.ts`（アプリ）
  - `drizzle.config.ts`（形の変更。手元・CI・Vercel のビルド）
  - `scripts/create-user.ts`（アカウントを作る）
  - `e2e/global-setup.ts`（画面のテストの準備）
- `docs/design.md` の「データベースのつながり方」に足す
  - データベースにつなぐときは、どこでも、接続先の URL をこの関数に通す。サーバーの証明書と接続先の名前を確かめるため
  - 理由：本番と Preview の接続先は Neon の連携が入れ、Preview は公開のたびに作られるので、人間が URL を書き換えられない。アプリの側で置き換えれば、5か所すべてで同じ確かめ方になる
  - 前提（崩れたら見直す）：`pg` が URL の `sslmode` を `ssl` の設定より優先する。`pg` の大きな版を上げるときは、`verify-full` の意味が変わっていないか確かめる
  - 新しくつなぐ場所（`new Pool()` など）を作るときも、この関数を通す
- `.env.example` は変えない（接続先は今のまま、Neon の画面の文字列を写せばよい）

### 選ばなかったやり方

- 人間が接続先の URL を `sslmode=verify-full` に書き換える（Issue の案）：手元と CI は直せるが、本番と Preview は連携が入れる値で、Preview は公開のたびに作られるので直せない。受け入れ条件を満たせない
- `new Pool()` に `ssl` の設定を渡す、環境変数 `PGSSLMODE` を置く：URL の `sslmode` が優先されるので、効かず、警告も消えない（「調べたこと」）

## 確かめ方

- どこでも、つなぐときにサーバーの証明書を確かめる：テスト（`connection-url.test.ts`。`sslmode=require` が `verify-full` になる、`sslmode` がないと `verify-full` が足される、ほかの値が残る）と、コードを見て確かめる（4か所すべてが関数を通している：`client.ts`・`drizzle.config.ts`・`create-user.ts`・`global-setup.ts`）
- どこでも、証明書の確かめ方についての警告が出ない：触って確かめる（手元で `npm test` と `npm run dev`、PR の CI のログ、Preview と本番の Vercel のビルドと関数のログに `SECURITY WARNING: The SSL modes` が出ない）
- 証明書を確かめられない接続先には、つながらない：コードを見て確かめる（関数が、URL にどんな `sslmode` があっても `verify-full` にしている）
- 本番と Preview で、今までどおり sign in でき、Home が出る：触って確かめる（タスクの PR の Preview と、マージ後の本番）
- 手元の開発・手元のテスト・CI は、今までどおり動く：テスト（今あるテスト・画面のテスト・CI がそのまま通る）
