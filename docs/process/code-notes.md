# コードを読むための補足

後から変えるときに「変えてよいか」を判断できるよう、判断の理由と前提（なぜそのやり方にしたか、何が崩れたら見直すか）を残す。
**1つの理由は1か所だけに書く**。置き場所は、影響する範囲で決める。

| 影響する範囲 | 置き場所 | 書く人・時 |
| --- | --- | --- |
| そのコードだけ | コードのコメント | 実装するとき |
| 複数の場所（整合性に関わる） | `docs/design.md`（今の設計） | 決まりができたタスクPR、または仕上げPRで |

- 迷ったら「この前提が崩れたら、直すのは1か所だけか？」。1か所ならコメント、複数なら `docs/design.md`
- コードはコメントだけで読めるようにする。全体の整合性は、ソースコード全体ではなく `docs/design.md` で確かめる
- `docs/design.md` の決まりに従っているだけのコードには、理由を書き写さない。普通とは違って見えるところだけ、`docs/design.md の「〇〇」` と見出しを1行で示してよい
- 見た目の決まり（色や部品の使い分け）は、`docs/design.md` ではなく `docs/ui.md` に書く
- `docs/changes/` は、比べた選択肢などの経緯の記録。理由の置き場所にはしない（AIは過去の `docs/changes/` を読まない）
- `docs/specs/` には動きだけを書き、理由は書かない

## `docs/design.md` に書くもの

- 全体の構成（フォルダ構成、層の分け方、どの層に何を書くか）
- データの持ち方と、その理由・前提
- どこでも守る決まり。ライブラリの使い方の注意で、コードの書き方を縛るものもここ（例：このデータベースの接続方法ではトランザクションが使えないので、1回の操作は1つのSQLにする）
- 「今どう作られているか」を現在形で書く。経緯は書かない

## ライブラリの資料

| 場所 | 書くこと | 書く人・時 |
| --- | --- | --- |
| `docs/libraries/<ライブラリ名>.md` | AIが書いたコードを読むため・アプリを開発するために必要な、ライブラリの前提知識。簡単な説明と、このプロジェクトで使っている部分 | 新しいライブラリを入れたタスクPRで、AIが下書きを書く |

- `docs/libraries/` は人間がコードを読むための資料。冒頭に、書いた時点のバージョンを書く
- 言語そのものの知識は書かない（エンジニアが持っている前提）。ドメインの知識やアプリ全体に特有の仕様・決まりも書かない（`docs/overview.md`・`docs/specs/`・`docs/design.md` に書く）
- 公式ドキュメントの写しにはしない。簡単な説明と公式へのリンクを書く
- AIは実装のときに読まない（古くなった説明を頼りに書かないため。使い方はインストール済みの型定義やドキュメントで確かめる）。そのため、AIに守らせたい注意は `docs/design.md` に書く

## コメントに書くもの・書かないもの

- 書くもの
  - 普通とは違うやり方を選んだ理由（例：データベースではなくアプリで並べ替える）
  - 外すと壊れる前提、崩れたら見直すべき前提（例：一覧は多くても数十件まで）
  - 試してだめだったやり方
  - 実装中に決めた細かいこと（`docs/changes/` の「設計」に書かれていない判断）
- 書かないもの
  - コードを読めばわかること（何をしているかの言い換え）
  - 複数の場所に関わる決まりと、その理由。これは `docs/design.md` に書く
  - `docs/design.md` にすでに書いてある理由の写し
